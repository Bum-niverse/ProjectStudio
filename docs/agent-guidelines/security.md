# 부록 B. 전역 실서비스 보안 지침

## 1. 목적과 적용 범위

개인정보, 인증 정보, 사용자 생성 콘텐츠, 결제 정보 또는 비용이 발생하는 외부 API를 다루는 모든 프로젝트에 적용한다.

다음 시점에는 보안 검토를 필수 작업으로 포함한다.

- 새 프로젝트의 최초 분석
- 실서비스 배포 전
- 인증, 권한, 데이터베이스, 파일 저장소, 공개 API, webhook, cron, 결제, AI API 기능을 추가하거나 변경한 후
- 개인정보 처리 범위 또는 공개 범위가 바뀐 후
- 보안 사고나 비밀정보 노출이 의심된 후

프론트엔드에 전달되는 코드, 환경변수, API 주소, public·publishable·anon key와 네트워크 요청은 사용자가 볼 수 있다고 가정한다. UI에서 버튼이나 메뉴를 숨기는 것은 권한 통제가 아니다. 권한과 데이터 경계는 서버와 데이터베이스에서 강제한다.

## 2. 보안 작업 절차

보안 검토 요청을 받으면 다음 순서를 따른다.

1. 저장소 구조, 배포 환경, 인증 흐름, 데이터 모델, 외부 노출 경로를 확인한다.
2. 수정 전에 전체 범위의 읽기 전용 감사를 수행한다.
3. 발견 사항을 심각도, 영향, 근거 파일, 공격 또는 오용 경로, 권장 수정으로 정리한다.
4. 실제 사용자 데이터나 제3자 시스템을 침해하는 방식으로 취약점을 검증하지 않는다.
5. 사용자가 수정까지 요청했거나 작업 범위상 명확히 허용된 경우에만 최소 변경으로 수정한다.
6. 정상 접근뿐 아니라 익명 사용자, 다른 계정, 권한 부족, 변조된 입력과 반복 요청을 테스트한다.
7. 코드 작성, 마이그레이션 파일 생성, 원격 환경 적용, 운영 검증을 서로 구분해 보고한다.

치명적 취약점이 확인되면 기능 개발보다 노출 차단과 비밀정보 교체를 우선한다. 다만 데이터 삭제, 파괴적 마이그레이션, 운영 서비스 중단과 같은 조치는 사용자 승인 없이 실행하지 않는다.

## 3. 필수 점검 영역

### 3.1 데이터베이스와 행 단위 권한

- 클라이언트에서 접근 가능한 모든 테이블, 뷰와 함수의 노출 범위를 확인한다.
- 개인정보 또는 사용자 소유 데이터는 기본 거부를 원칙으로 하고, 명시적인 정책만 허용한다.
- Supabase 등 RLS를 지원하는 환경에서는 노출 테이블의 RLS 활성화와 정책을 함께 검증한다.
- 개인정보 테이블에 무조건 참이 되는 읽기·쓰기 정책을 두지 않는다.
- 생성, 조회, 수정과 삭제 각각에 대해 소유자, 관리자, 공개 사용자 조건을 분리해 확인한다.
- 익명 키, 로그인 사용자, 다른 계정과 service role의 실제 결과를 각각 검증한다.
- 마이그레이션 파일을 만들었다는 이유만으로 적용 완료라고 보고하지 않는다. 대상 환경 적용과 정책 활성 상태를 별도로 확인한다.

### 3.2 파일 저장소

- bucket과 파일을 공개 또는 비공개로 분류하고 목적과 일치하는지 확인한다.
- 신분증, 계약서, 개인 사진, 내부 문서와 같은 민감 파일은 공개 bucket에 저장하지 않는다.
- 비공개 파일은 소유권 정책과 짧은 만료 시간의 signed URL을 사용한다.
- 업로드 시 파일 크기, MIME type, 확장자, 파일명, 저장 경로와 악성 콘텐츠 위험을 검증한다.
- 다른 사용자의 경로 추측, 직접 URL 접근과 목록 조회가 차단되는지 테스트한다.

### 3.3 인증, 세션과 비밀정보

- 비밀번호, API key, service role key, private key, webhook secret와 세션 토큰을 코드, URL query, 로그 또는 클라이언트 번들에 넣지 않는다.
- 클라이언트가 전달한 사용자 ID나 역할을 신뢰하지 않고 서버에서 검증된 세션을 기준으로 판단한다.
- 관리자 권한은 서버와 데이터베이스에서 확인한다. 이메일 문자열 비교나 UI 조건문만으로 부여하지 않는다.
- OAuth에는 허용된 redirect URI, `state`, PKCE 등 공급자가 제공하는 보호 장치를 적용한다.
- 회원가입 허용 범위, 이메일 확인, 비밀번호 정책, 계정 복구와 redirect 허용 목록을 점검한다.
- 비밀정보 노출이 의심되면 코드에서 제거하는 것만으로 끝내지 않고 해당 값을 폐기·교체한다.

### 3.4 객체 소유권과 IDOR

- URL, body 또는 query의 `userId`, `playlistId`, `documentId` 같은 식별자는 권한의 근거로 사용하지 않는다.
- 모든 조회, 수정, 삭제, 다운로드에서 서버 또는 데이터베이스가 리소스 소유권과 역할을 확인한다.
- 계정 A가 계정 B의 식별자를 사용해 접근하는 교차 계정 테스트를 작성한다.
- 존재 여부 자체가 민감한 경우 오류 응답으로 리소스 존재를 불필요하게 노출하지 않는다.

### 3.5 cron, webhook과 서버 간 호출

- 공개 URL이라는 이유로 신뢰하지 않는다.
- cron endpoint는 전용 secret 또는 플랫폼 인증으로 보호한다.
- webhook은 공급자 서명, timestamp와 replay 방지를 검증한다.
- 중복 전송을 고려해 idempotency를 보장하고 처리 이력을 안전하게 관리한다.
- secret 또는 서명이 없거나 잘못된 요청이 거부되는지 테스트한다.

### 3.6 API 응답과 데이터 최소화

- `select *`, 전체 객체 직렬화와 데이터베이스 row의 무가공 반환을 피한다.
- 용도별 DTO 또는 응답 schema로 허용 필드만 명시한다.
- 이메일, 전화번호, 주소, 내부 메모, 권한 정보와 결제 식별자는 필요한 요청에만 최소한으로 반환한다.
- 목록, 검색, 내보내기와 관리자 API의 과다 노출을 별도로 확인한다.

### 3.7 입력 검증과 주입 공격

- body, query, path, header, cookie, 파일과 외부 API 응답을 신뢰 경계의 입력으로 취급한다.
- 서버에서 타입, 길이, 범위, 형식, 허용값과 중첩 깊이를 검증한다.
- SQL은 parameter binding을 사용하고 문자열 결합으로 쿼리를 만들지 않는다.
- 운영체제 명령은 가능한 한 사용하지 않으며, 필요한 경우 shell 문자열 결합 대신 안전한 인자 전달을 사용한다.
- 외부 URL 요청은 프로토콜과 host allowlist, redirect, 사설망 접근을 검증해 SSRF를 방지한다.
- 예상하지 못한 필드는 제거하거나 거부하고 mass assignment를 방지한다.

### 3.8 XSS, CSRF와 브라우저 경계

- 사용자 입력을 HTML로 직접 렌더링하지 않는다.
- `dangerouslySetInnerHTML` 또는 동등 기능이 필요하면 검증된 sanitizer와 제한된 정책을 사용한다.
- Markdown, rich text, SVG와 외부 embed를 별도 공격 표면으로 검토한다.
- cookie 기반 변경 요청에는 SameSite, CSRF token 또는 Origin 검증 등 구조에 맞는 보호를 적용한다.
- Content Security Policy는 실제 리소스와 호환되게 설계하고 report-only 검증을 거쳐 강화한다.

### 3.9 남용 방지와 비용 통제

- 로그인, 가입, 비밀번호 복구, 검색, 업로드, 이메일 발송, AI·번역·지도·결제 API에 서버 측 rate limit과 quota를 검토한다.
- 비용이 큰 작업은 인증, 사용량 제한, 중복 방지와 최대 입력 크기를 적용한다.
- 필요하면 CAPTCHA나 이메일 확인을 보조 수단으로 사용하되 유일한 방어로 삼지 않는다.
- 예산 알림과 공급자 한도를 설정하되 애플리케이션의 권한·사용량 통제를 대신하지 않는다.

### 3.10 보안 헤더와 전송 보안

- HTTPS를 전제로 HSTS 적용 가능성을 검토한다.
- `frame-ancestors` 또는 `X-Frame-Options`, `X-Content-Type-Options: nosniff`, 적절한 `Referrer-Policy`와 `Permissions-Policy`를 검토한다.
- CSP는 무분별한 wildcard와 `unsafe-inline` 사용을 피하고 실제 배포 응답에서 확인한다.
- cookie에는 용도에 맞게 Secure, HttpOnly와 SameSite 속성을 설정한다.

### 3.11 로그, 저장소와 배포 산출물

- 비밀번호, token, authorization header, cookie, 주민번호 등 고유 식별정보와 민감 개인정보를 로그에 남기지 않는다.
- 필요한 식별자는 마스킹 또는 비식별화하고 로그 접근과 보존 기간을 제한한다.
- `.env`, 원본 데이터, dump, 업로드 파일과 인증서가 Git 또는 배포 산출물에 포함되지 않는지 확인한다.
- 현재 파일뿐 아니라 Git 이력의 비밀정보 노출 가능성도 점검한다.
- 클라이언트 source map과 오류 추적 도구가 소스·환경정보·사용자 데이터를 과도하게 노출하지 않는지 확인한다.

### 3.12 오류 응답

- 사용자 응답에는 내부 stack trace, SQL, 경로, secret, 공급자 원문 오류와 상세 인프라 정보를 노출하지 않는다.
- 클라이언트에는 해결 가능한 일반 오류와 추적 ID를 제공하고, 상세 정보는 접근 통제된 서버 로그에 기록한다.
- 인증 실패, 권한 부족, 존재하지 않는 리소스와 유효성 오류의 응답 정책을 일관되게 유지한다.

### 3.13 개인정보 수명주기

- 필요한 정보만 수집하고 목적, 보존 기간, 삭제 범위를 명확히 한다.
- 계정 삭제 시 데이터, 파일, 파생 데이터와 백업의 처리 정책을 확인한다.
- 전송 중과 저장 시 암호화, 관리자 접근 기록, 백업 복구와 데이터 내보내기를 검토한다.
- 법적 신고·통지 기한과 절차는 고정된 숫자를 전역 규칙에 하드코딩하지 않고 사고 발생 시 관할 지역의 최신 공식 지침을 확인한다.

## 4. 최소 보안 검증표

관련 기능에 따라 다음 시나리오를 자동화하거나 수동으로 검증한다.

- 로그아웃 또는 익명 상태의 비공개 데이터 접근
- 계정 A가 계정 B의 리소스를 조회·수정·삭제하는 요청
- 일반 사용자의 관리자 기능 접근
- private 파일의 직접 URL과 추측 가능한 경로 접근
- 서명 또는 secret이 없거나 재사용된 webhook 요청
- 비정상 타입, 과도한 길이, 추가 필드와 경계값 입력
- 저장형·반사형 XSS 가능 입력과 rich text 렌더링
- 반복 요청 시 rate limit, quota와 idempotency 동작
- 실제 배포 응답의 보안 헤더와 cookie 속성
- 운영 환경의 마이그레이션, RLS와 storage policy 적용 상태

테스트는 실제 타인의 데이터에 접근하거나 운영 데이터를 훼손하지 않는 격리된 계정과 환경에서 수행한다.

## 5. 완료 기준과 보고

보안 관련 작업은 다음 조건을 충족해야 완료로 보고할 수 있다.

- 발견 사항과 위험도가 근거와 함께 기록되어 있다.
- 정상·비정상·교차 계정 시나리오를 검증했다.
- 코드, 마이그레이션, 배포 설정과 운영 적용 상태를 구분했다.
- 새 비밀정보가 코드, 로그, Git diff와 빌드 산출물에 포함되지 않았다.
- 검증하지 못한 운영 설정과 잔여 위험을 명시했다.
- 배포 후 실제 응답과 권한 정책을 확인했다.

결과 보고에는 최소한 다음을 포함한다.

- 감사 범위와 위협 모델
- 심각도별 발견 사항
- 수정 내용과 변경 파일
- 실행한 보안 테스트와 결과
- 운영 환경 적용 여부
- 검증하지 못한 항목과 잔여 위험
- 필요한 비밀정보 교체, 모니터링 또는 후속 작업

## 6. 사고 대응

노출 또는 침해가 의심되면 다음 순서로 대응한다.

1. 추가 노출을 차단하되 증거를 훼손하지 않는다.
2. 영향받은 데이터, 사용자, 기간, 계정과 시스템 범위를 확인한다.
3. 관련 key, token, 세션과 자격증명을 폐기·교체한다.
4. 로그와 변경 이력을 보존하고 재발 경로를 차단한다.
5. 관할 지역의 최신 공식 법률·기관 지침에 따라 신고와 사용자 통지 의무를 확인한다.
6. 수정 후 전체 보안 감사를 다시 수행하고 원인, 영향과 재발 방지책을 문서화한다.

이 지침은 공개된 [Basic Security Guide for Vibecoders](https://teriwell.notion.site/basic-security-guide-for-vibecoders-399076c0d70980a5b8ced532800aeb35)의 점검 항목을 Codex의 저장소 분석, 최소 변경, 테스트와 작업 보고 방식에 맞게 재구성한 것이다.
