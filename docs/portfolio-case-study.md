# ProjectStudio 포트폴리오 개발 기록

## 왜 만들었는가

첫 검증 프로젝트를 기획하면서 PRD, 기능명세, 유저플로우와 시스템 설계가 채팅과 문서에 흩어졌고 변경 이유와 구현 상태를 함께 추적하기 어려웠다. 기존 시각 기획 도구는 협업형 SaaS에 가깝지만 ProjectStudio의 목표는 한 명의 개발자가 아이디어부터 코드·테스트까지 연결하는 로컬 작업대다. 그래서 실제 프로젝트를 검증 사례로 사용하면서 반복되는 기획과 검토 절차 자체를 제품으로 만들었다.

## 핵심 기술 선택과 이유

- **Tauri 2 + Rust**: 파일·Git·SQLite 접근을 명시적인 command 경계에 두고 작은 Windows 배포 산출물을 유지한다.
- **React + TypeScript + Vite**: 노드 캔버스와 편집 패널을 컴포넌트화하고 기획 데이터 계약을 strict type으로 검증한다.
- **SQLite**: 별도 서버와 구독 비용 없이 프로젝트·불변 리비전·사용자 배치를 로컬에 보존한다.
- **React Flow**: 범용 그래프 상호작용 대신 제품 고유의 레이아웃과 구조화 모델에 집중한다.
- **Codex CLI**: 별도 API 키 서버 없이 로컬 인증을 활용하고 결과는 JSON 계약과 결정론적 품질 검사기로 검증한다.
- **단일 구조 모델 + 다중 뷰**: 이미지를 원본으로 삼지 않고 nodes·edges·links·constraints를 저장해 C4, 런타임, 배포, 개발 관점을 파생한다.
- **명시적인 프로젝트 유형**: 키워드 추론에만 의존하지 않고 사용자가 유형을 선택해 불필요한 사용자 화면 흐름 생성을 막는다.

## 막힌 지점과 해결 과정

1. 규칙 기반 생성은 일반 프로젝트에서 첫 검증 프로젝트 수준의 상세도를 만들지 못했다. PRD는 재현 가능한 규칙으로 시작하되 하위 산출물은 Codex CLI가 구조화 생성하는 하이브리드 방식으로 전환했다.
2. 유저플로우가 기능명세를 펼친 그림이었고 RLS·URL 검증 같은 내부 처리까지 섞였다. 기능명세는 제품 범위 트리로, 유저플로우는 `화면 → 사용자 행동 → 사용자에게 보이는 결과`의 가로 스윔레인으로 분리했다.
3. 노드 수가 늘면 글자·노드·선이 겹치고 테마 변경 뒤 캔버스가 사라졌다. 열 기반 레이아웃, 대주제 시트, 분기 라우팅, 렌더 이후 fitView와 테마별 토큰을 도입했다.
4. 자유 다이어그램만으로는 설계와 구현의 불일치를 알 수 없었다. 기능·흐름·코드·테스트 링크, 불변 리비전, ADR, C4 뷰와 drift 후보 검사를 추가했다.
5. LLM이 유효한 JSON을 내도 관계 누락과 도메인별 검토 공백이 남았다. 웹·앱, 머신러닝, 데이터 분석을 분류해 공통 구조와 유형별 위험을 검사하는 품질 게이트를 추가했다.

## 품질 검사기의 범위

공통 검사는 기능 계층, 수용 기준, 사용자에게 보이는 흐름, 고립 노드, 시스템 책임과 추적 링크 무결성을 확인한다. 웹·앱은 화면 상태와 접근 경계를, 머신러닝은 데이터 출처·분할·누수·기준선·평가·재현성을, 데이터 분석은 스키마·병합 카디널리티·결측·중복·이상치·데이터 계보를 추가 검사한다.

검사 실패는 생성 결과를 삭제하지 않는다. `통과 / 검토 필요 / 보완 필요`와 근거를 표시해 사람이 수정·승인할 수 있게 한다.

## 현재 한계와 다음 검증

- Codex CLI는 이 대화의 기억을 공유하지 않으므로 PRD와 명시적 생성 계약의 품질이 중요하다.
- 키워드 기반 유형 분류는 혼합형 프로젝트에서 오분류할 수 있어 사용자가 유형을 고정하는 기능이 후속 대상이다.
- 품질 점수는 완성도를 보증하지 않으며 누락을 빠르게 찾는 검토 우선순위다.
- 향후 검사 결과에서 해당 산출물로 이동하고 승인된 수정 이력을 품질 추세로 보여줄 예정이다.
